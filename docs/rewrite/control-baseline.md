# Registration and control baseline

OpenSpec task 1.6 records **47 cases and 588 observed transitions** from immutable baseline `checkpoint-clojure-baseline`: 38 unchanged original fixture assertions and nine supplemental Managed Bot scenarios. This is original-only evidence for later candidate comparison, not an implementation or release-gate claim.

Run `bun scripts/rewrite/control-baseline.ts check`. It runs the original fixtures in two independent subprocesses, compares full transcripts, then verifies the checked-in [manifest](../../test/rewrite/fixtures/control-baseline.json). Complete synthetic API arguments/results/errors, per-transition rows from all six tables and logs regenerate at ignored `data/rewrite/evidence/control-baseline.json`. The manifest stores exact serialized transcript/state digests, transition order and original inventory IDs/source hashes. `record` explicitly replaces it; investigate differences before accepting a replacement.

All 38 original cases retain their existing assertions. A process-local native Bun module mock registers those original test functions, runs them sequentially and executes their cleanup hooks. It substitutes observational Store/Bridge subclasses: original workflow methods still run, API proxies record fixture calls/results, and database wrappers record state after direct SQL mutations or an outer workflow completes. Original files and fixture API implementations are unchanged. The harness validates every selected name against the immutable inventory and rejects missing selections/references. The supplemental provider rejects unscripted methods; global fetch rejects provider networking.

Clock/timezone and UUID/random-integer/AES-nonce inputs are fixed only in these disposable processes. Fixed entropy is never exposed through the application runtime. Token ciphertext format and authenticated encryption still run original code; the regression confirms the sealed token is not plaintext. Raw durable JSON, hashes, identities, API order, absent/null object fields, scopes, receipt results and retry/uncertainty distinctions remain in the observations.

One additional original behavior is explicitly characterized: when registration fails after the bot row has been saved (logout, webhook or menu setup), a repeated registration finishes setup but treats the bot as existing and omits the binding prompt. Token-fetch failure leaves no bot row, so its successful retry includes the prompt. This observation is not a proposed fix or an approved correctness exception. The 20-button cap likewise retains action rows for all 22 pending contacts while displaying only 20 choices.

Candidate control implementation/comparison, broader history/Status/metadata recordings and all eight acceptance gates remain pending. Generic callback correctness candidates, poll selections, edits, reactions and revocations belong to task 1.7. No real registration, account data, provider access or deployment is involved.
