# Migration plan

Decision update (2026-11-10): architecture is finalized. [08 Implementation specification](08-implementation-specification.md) governs future authorized work, including correctness exceptions and backward-compatible schema extensions. Earlier strict-parity/pending-review wording below is historical where it conflicts with that contract. Implementation and deployment remain unauthorized.

This document authorizes no implementation or deployment. Review the architecture first. Stages below preserve all observed behavior, including odd transitions and legacy checkpoint formats.

1. **Freeze the oracle and evidence.** Record source revision, runtime/image/dependency hashes and baseline results; inventory all current commands/events using document 02. Confirm actual deployment revision separately from repository code. Acceptance: every inventoried feature has fixture owner/location and V/U/D/N status; secrets absent from corpus.
2. **Prove nbb runtime.** Pin candidate nbb in an isolated candidate tree, run document 04 gates in Bun 1.4.2 target Linux image, verify worker launcher/resource paths, system codecs, graceful/forced exit and no Node process. Acceptance: all required capabilities execute, unresolved incompatibilities have a concrete verified solution; no production code or identity altered.
3. **Build offline behavioral oracle.** Record sanitized event/API transcripts and synthetic state snapshots from current modules; fake APIs forbid network. Freeze time/randomness and generate goldens, including crash windows and partial sends. Acceptance: original code deterministically reproduces corpus, no live accounts are needed, known test skips explicitly tracked.
4. **Implement persistence and pure rules after approval.** Keep SQL/schema, encrypted payload format and all externally durable keys; compare old/new reopening of synthetic and privately held cloned state. Port formatting, parsing, aliases, routing and queue selection. Acceptance: exact observable formatting/UTF-16 entities; identical selected jobs and durable state; cross-runtime token decrypt check by digest only.
5. **Implement adapters and core relay.** HTTP authentication, admission, conservative API classification, effects, private/group text/replies then all media. Acceptance: exact API traces, receipts, idempotency keys and restart outcomes under shared fixture driver. No replay mode may reach real network.
6. **Implement control workflows.** Official Managed Bots/token refresh/binding/readiness, linking/unmirror, mentions, reactions/revocations, history/Status, metadata, TTL/clear menus and administrative tooling. Acceptance: entire document 02 inventory and all original tests represented; failure paths and legacy migration jobs compared, no new product behavior.
7. **Rehearse operations.** Export/import stopped synthetic or private cloned volumes; run Linux codec and Docker suites, identity/config preservation and 24-hour-plus accelerated/real soak. Acceptance: zero unexplained trace/state differences, bounded backlog/memory, file permissions/volume mounts verified, rollback rehearsed with candidate writes.
8. **Controlled single-writer cutover.** Schedule owner-approved window. Stop old ingress/worker and confirm process stopped; preserve current consistent DB/WAL backup, encryption configuration, media/Telegram volumes and matching old image. Account for queued provider retries, TTLs and active history/uncertain jobs. Start one candidate on current state with unchanged callback address if possible; never drop pending Telegram updates. Observe one owner-authorized contact/group exchange, then monitor errors/queue/mappings and background controls. Acceptance: expected mappings, no duplicate side effects, menus/Managed Bots/Status/history still work; compare deterministic receipt evidence privately.

No two live bridges may run against the same accounts, even on different database copies: each copy would independently send effects, alter webhooks and metadata, and compete for updates. Offline shadowing uses captured events and fake API only. A maintenance CLI opening Store must not perform startup recovery while another worker runs.

Rollback: stop candidate completely; preserve its latest state and logs before restarting old image against the **current compatible database** and same identity/config/volumes. Do not restore an earlier database just to revert code: it forgets new receipts and can duplicate sends. Verify candidate writes remain readable by old code before cutover. If state is corrupted, stop both, preserve both snapshots, reconcile provider deliveries and journal before any restore/retry. Callback changes, if required, must be reversed with drop_pending_updates=false and recorded. Re-pairing WhatsApp or provisioning replacement tokens is not rollback.

Stop/go criteria: no unexplained differences in required fixture corpus; all default, opt-in codec and transfer checks pass in target environment; uncertain sends remain explicitly blocked; all runtime U items resolved for deployed paths. Live behavior not reproducible offline must have approved canary verification and rollback criteria. Keep changes focused; performance/concurrency/schema redesign waits until parity is accepted.
