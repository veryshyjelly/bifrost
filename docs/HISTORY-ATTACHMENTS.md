# History and attachments

The Go history and attachment capabilities run through the fenced worker in isolated native SDK/PostgreSQL tests. Diagnostic `serve` still does not dispatch. Runtime composition and the remaining message-change workflows are tracked in [RUNTIME.md](RUNTIME.md).

History prompts freeze the owner, account/session, bot, topic, binding, destination and original prompt receipt. A choice starts no fetch or live hold until accepted. Selection and prompt expiry are separate durable operations. Counts are 1–2000, default 20; requests above 100 use deep history. The entire available batch is stored before delivery, with quote parents ordered before children. Only that WhatsApp conversation is held while its run is active; terminal or uncertain failures release the history hold without deleting the topic.

A definitively refused history item fails its run and leaves subsequent items waiting for review; it is not silently skipped. Once the cause is repaired, `bifrost review --job ID --action retry` resumes the original frozen batch and packet keys, preserving completed copies and headings. Unknown sends still require explicit evidence before retry. Starting a new import is separate from resuming the old run.

Telegram can still reject a native bot mention with `BOT_ACCESS_RESTRICTED`. For this definitive text-send refusal only, the master verifies the saved bot ID and username in the destination. The worker atomically retains the original request as discarded and freezes a separate link fallback: text, sender, destination, reply and other entities stay unchanged. The next effect uses its own key and receipt. No bot access settings are changed. Changed usernames, rate limits and unknown native sends cannot select this fallback; an unknown fallback send also requires review. History recovery uses the original saved batch and completed receipts throughout.

Import all creates new copies and quotes their fresh parents. Skip existing checks retained destination receipts; it emits no empty day headings for skipped items. A known partial live plan can transfer atomically to its history item: original effect keys, presentation, file references and completed receipts survive. Running, sending and uncertain work cannot be adopted. Explicit review remains necessary for uncertain sends. History retry uses the stored batch and prepared media rather than fetching new source bytes.

Incoming packets support text, photos, video, audio, voice, stickers, documents, locations, contact cards and polls. All use native SDK methods, literal text/entities and scoped quote mappings. Captions that exceed the caption budget are retained as separate text. A definitive native media refusal can send the untouched original document; a deferred caption label preserves a caption that would overflow after adding the fallback notice. Rate limits and ambiguous mutations never trigger that fallback.

Outgoing attachments use authenticated Telegram GetFile and its native download URL, or a file within the configured shared Telegram directory. The original and any conversion are stored before the send effect. The ledger stores a hash/size reference; base64 is generated only for the SDK call. Locations retain zero coordinates, contacts use native cards, polls retain multiple-choice settings, and voice messages set PTT only on send-audio. A confirmed send records its mapping and media archive and queues an independent read receipt. An unknown send remains for review. A definitive sticker refusal uses a separate stable original-document effect key.

Owned media objects live below `bifrost-go-assets` in the configured media root and are content-addressed, bounded and verified on read. History can reuse them and retained Telegram media before requesting stored OpenWA media. Only a documented stored-cache miss permits source retrieval. Route/session errors remain retryable. Status retrieval never follows a supplied external URL or marks a Status viewed. Abandoned `.incoming-*` files and `.codec-*` work directories older than 24 hours are eligible for cleanup. Frozen objects and existing media are retained.

Sticker conversion uses the retained Pillow helper, ffmpeg/ffprobe and a native Go Chromium driver. Outgoing WhatsApp WebP must fit 1,000,000 bytes including metadata and pass RIFF/container, decoding, dimensions and timing checks. Telegram's separate static and animated limits remain enforced. The real codec container tests include large static/animated WebP and the historical nonzero-start-frame TGS fixture, checking motion and transparency.

The embedded Lottie light renderer is lottie-web 5.13.0 under its bundled MIT license. It was obtained from the exact npm release tarball with SHA-512 integrity `sha512-+gfBXl6sxXMPe8tKQm7qzLnUy5DUPJPKIyRHwtpCpyUEYjHYRJC/5gjUvdkuO2c3JllrPtHXH5UJJK8LRYl5yQ==`. Rendering uses a data-only page, blocks network resources and rejects external Lottie assets and expressions. Node is not a runtime dependency. The Go driver is chromedp v0.23.0 with its pinned protocol dependency; the image pins Pillow 13.0.0.

Coverage includes scoped choice reuse/cancellation, fetch freezing, source-specific holds, native text/image history and fresh quotes, completed destination skipping, partial-plan adoption, uncertain-send preservation, immutable retry bytes, caption fallback and separate send/read work. Full operational acceptance remains dependent on the composition/import work in the completion checklist.
