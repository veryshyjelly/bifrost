# Managed Telegram bots

`internal/bots` implements native managed-bot registration, encrypted credential lookup, explicit local Bot API migration/webhook setup, contact creation and scoped binding. The provider adapter uses the maintained Telegram SDK methods; no token appears in effect requests, receipts or settings plans. Latest stable SDK versions were re-resolved before implementation and remain OpenWA Go v0.11.1 and go-telegram/bot v1.28.0.

Registration validates the owner and native update again under the live claim, then commits the encrypted credential, bot identity, registration replay record and setup job together. AES-256-GCM retains the legacy envelope format. The client pool reads current credentials for each request, so rotations/imports need no cache invalidation. Registering or starting a bot does not establish migration eligibility.

Setup records a confirmed hosted-API logout before verifying the bot's identity through the local API. It then records local migration eligibility and installs the authenticated webhook without dropping pending updates. Webhook settings retry independently as idempotent settings; menu and creation-notice jobs follow on the same bot stream. Uncertain cloud logout stays in review and cannot advance setup. Confirmed logout receipts remain reusable migration evidence across superseded setup configurations; stale configurations/credentials can close only definitely unsent work.

`/create` uses the current conversation or the immutable sender behind a mapped group reply. Existing bindings produce the original guidance. Pending creation and its frozen prompt commit together, leaving master routing available at Telegram's bot limit. Newly registered bots offer at most twenty pending contacts. A binding choice validates account/session, owner, master bot, private destination, original prompt receipt and expiry; its binding, consumption, sync admission and confirmation commit together. A bot bound to another canonical contact cannot be reassigned through a stale choice. An unstarted bot does not retire its inbox; started bots use the existing independent retirement workflow.

Migrations 18–19 preserve credentials, setup/registration journals, pending provisions and consumed choices. Import must retain this evidence and the original encryption key. Isolated PostgreSQL/native SDK fixtures cover registration rollback, encryption, explicit migration, webhook retry, uncertain logout, native participant selection, routing preservation and single-use binding. Runtime composition and import remain separate completion tasks; no live provider setup is performed by these tests.
