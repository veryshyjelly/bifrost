# Metadata snapshots and text updates

`internal/metadata` implements the source-snapshot and Telegram text stages of metadata refresh, followed by [resumable picture caching/uploads](METADATA-PICTURES.md) and [permission advice, owner commands and sealed completion notices](METADATA-ADVICE.md). It accepts scoped group/contact `sync_metadata` work through a claimed job, preserves provider metadata in PostgreSQL and freezes each intended update. These stages are tested through the worker with native SDK loopback fixtures. The [durable run coordinator](METADATA-RUNS.md) now supplies admission, retry/outcome collection, discovery, source serialization, fan-out/coalescing and persistent cron. Explicit `run` composes these capabilities after native identity and callback verification; diagnostic `serve` remains passive. `serve` still does not dispatch automatically.

## Source preservation and identity

OpenWA may return a canonical phone contact ID for a LID lookup. The adapter accepts it only when the native `Contacts.Phone` response names the original requested LID and its explicit phone value matches the returned contact ID. The metadata record keeps the requested LID; no alias, route or bot binding is changed. Missing, mismatched or failed proof cannot update the profile. The contact's display `number` is never used as phone evidence.

Group refresh requires a nonblank name and a complete native participant list. Missing/null rosters, malformed participant IDs, lookup errors and malformed descriptions cannot replace an existing roster or identity. A valid empty roster is distinct from an unavailable roster. Source snapshots, mention rosters, current route names, prior topic names and complete text plans commit together under the account directory lock and a live claim. Failed plan writes roll everything back. Snapshots include the OpenWA session; verified contact aliases share the same canonical snapshot scope. Newer snapshots make older unfinished text plans obsolete.

The maintained OpenWA SDK v0.11.1 represents `GroupInfo.Description` as a string, losing the unavailable/empty distinction. The adapter uses the SDK's public `Client.Do` extension with an embedded native group model and optional description. The SDK still owns authentication and transport. An absent/null description preserves Telegram data; an explicit empty description may clear it. Contact reads use native `Contacts.Get`, preferring nonblank name, then push name, then stored name or ID. Metadata never treats a LID display number as phone evidence. Existing verified aliases and bot bindings are preserved; ambiguous independently routed aliases require reconciliation.

## Text destinations and recovery

An active management inbox refresh changes only its topic name. Retired inbox topics are not edited. A group's metadata cannot overwrite the shared management group's title or description. Mirror updates require a private Telegram group, including no primary or active usernames, and the master bot's native Change Group Info right. Missing rights produce a persisted warning for later scoped permission guidance. Contact bot name/description updates use the existing binding and work without a direct route; refresh creates neither a bot nor a route.

Text follows the original control-character filtering and UTF-16 budgets: 128 units for topic/group names, 255 for group descriptions, 64 for bot names and 512 for bot descriptions. Plans keep their complete values, destinations, session and source snapshot. Each part has an independent effect key and confirmed receipt. Retry and reopened consumers reuse the plan without another WhatsApp lookup or repeating confirmed setters. A lost setter response can retry the same value because these operations are idempotent; native already-set responses are successful, while permission and rate refusals remain visible.

Before each part, the store checks the account claim, current route, retirement state, return generation, canonical identity, bot binding and latest snapshot. Mirror privacy is read again before text setters. A later route, public username, binding or generation cannot retarget an old plan. Successful topic names are recorded separately from refreshed source names, so a failed rename does not make a later request incorrectly believe it was applied. A failed local completion write reconciles confirmed receipts without another setter.

`TextComplete` records only these text stages. It is not a completed metadata run. Migration `00014_metadata_text.sql` retains snapshots, frozen plans and destination-scoped applied topic names. These records and their effect receipts must be included in existing import/recovery before runtime startup. The WhatsApp interface exposes reads only; this capability performs no WhatsApp message, history, read-state, membership or profile mutation.
