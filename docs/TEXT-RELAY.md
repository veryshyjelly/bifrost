# Text relay components

`internal/relay` now implements typed incoming/outgoing text capabilities over the fenced worker and native provider SDKs. `internal/presentation` ports the literal-text/native-entity formatter. These are tested components, not an enabled live bridge: `serve` still does not start the worker or install callbacks.

The caller must supply verified canonical identities and select the appropriate capability before invoking a text operation. The [native dispatcher](DISPATCH.md) now provides source normalization and worker handler selection. [Identity and mention components](IDENTITY-MENTIONS.md) provide alias-aware directory lookups, mention rendering and roster validation through `relay.Options.Mentions`. Commands and edits still require dedicated handlers; new mention-dependent text requires the resolver. Command/media handlers, edits, repair/cleanup, managed-bot credentials and the legacy importer remain pending. Unsupported messages are retained through the normal failed-job/review protocol rather than forwarding a partial text representation.

## Rendering and frozen plans

Master text relays use the original bold, WhatsApp-linked sender name and body on one line. A member bot omits redundant names. Phone-originated messages retain `You · sent from WhatsApp`; an unavailable self identity uses the generic launch link rather than guessing the peer's phone. Untrusted text stays literal, with no parse mode. Native link entities disable previews as before.

All offsets and text budgets use UTF-16 units. Emoji pairs are not split; native date/time spans stay atomic. Compact and legacy history headers, timezone clocks and day labels are available in the formatter for the future history workflow. Timezone data is embedded through the standard Go library. Fixed golden fixtures were generated by the original TypeScript formatter under Node; Go tests compare complete text, entities and split packets.

A text plan freezes the destination bot/chat/topic, presentation, quote and every packet before its first send. Preparation rechecks the current route. A subsequent retry uses the saved plan, even if routing or display metadata changes. Each external effect also retains its own original request and immutable receipt. Replaying a completed part requires no current provider call or token lookup.

Outgoing effects preserve the original `send:<chat>:<message>` key, with the bot ID included for private chats. The OpenWA `Idempotency-Key` remains the SHA-256 of that exact stable key, without an attempt suffix. Incoming text effects retain the `event:to:bot:destination:text:part` structure; the separately stored source plan prevents a second webhook for the same source message from creating another delivery. Legacy plan reconstruction remains the explicit importer's responsibility.

## Mappings, quotes and echoes

Migration `00005_text_relay.sql` adds account-scoped plans and message mappings, plus the observation deletion marker needed by cleanup. The mapping is reconciled from the ledger's confirmed receipt, never from a caller-supplied success claim. Mapping writes and cleanup observations commit together. If a local write fails after sending, retry reads the saved receipt and repairs the mapping without resending.

Private Telegram message IDs are scoped by bot; group IDs share a group scope. Quotes require the same WhatsApp conversation, destination and effective topic, and cannot reuse copies cleared in either mapping or observation state. Whole-group mirrors ignore incidental Telegram reply-thread IDs. Native reply parameters permit delivery if the quoted Telegram message disappears later, without recreating it.

An outgoing WhatsApp send echo can arrive before its mapping write. Echo checks therefore recognize both mappings and confirmed outgoing effect receipts. While a same-chat send is sending/uncertain without a known matching receipt, owner-originated events defer rather than being mistaken for phone-originated messages. Peer incoming messages remain independent. Tests exercise this with concurrent workers and a held native SDK request.

## Reads and pauses

Successful outgoing completion atomically records its mapping and queues a separate management read job. `MarkRead` uses the native OpenWA SDK as an idempotent read-state update. A read failure cannot replay the original send. Incoming relays and echo suppression do not mark WhatsApp content read.

If a route becomes muted/ignored during a partial retry, confirmed parts remain mapped and only definitely unsent parts close in the terminal `discarded` state. Missing unsent effects are created and closed atomically from the frozen plan. Sending/uncertain effects cannot be cancelled through this operation, and completed receipts are never erased. Completion after a cancelled outgoing send does not queue a read unless a send actually succeeded.

## Verification boundary

Real isolated PostgreSQL tests combine the worker with both native SDKs and loopback provider fixtures. They cover multipart rate refusal/retry, changed routes/presentation, quoted replies, private bot ID overlap, foreign and cleared quotes, wrong-owner filtering, native whole-group reply threads, stable keys, receipt-before-mapping echo suppression, in-flight echo deferral, pause safety and independent read failures. No live provider operation, callback change or cutover is part of this slice.

The existing 1,000,000-byte outgoing WhatsApp sticker budget remains unchanged. This text work does not enable media or history delivery.

The dispatcher can now attach the [mention-refusal notice handler](MENTION-PICKER.md). Definite mention validation errors then produce a frozen temporary Telegram notice without sending or reading WhatsApp content. Provider failures and uncertain outcomes retain the text capability's existing delivery handling.
