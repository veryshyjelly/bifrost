# Passive Status archive

The isolated native workflow stores contact Status posts in one account/management-scoped `WhatsApp Status` topic. Startup refresh admission requires an actual master local API migration record; registration and Start do not establish eligibility. `/statuses` ensures the topic, freezes its linked confirmation and queues a refresh. Runtime webhook registration remains a separate composition responsibility and must explicitly include `status.received`.

Topic creation has a persistent originating-job owner. Unknown creation acknowledgements stay uncertain and block competing setup attempts. Refresh batches are sorted by native posting time and frozen before jobs are queued. A permanent account/post key arbitrates webhook/refresh races, retains original job ownership and prevents refresh from adopting unknown sends. Existing Telegram copies survive source expiry. Cleared copies and posts skipped while muted are not backfilled by later refreshes.

Text, image, video and voice packets use the native attachment pipeline with linked author attribution and native posting time. Status URLs never enter frozen post values or download requests: bytes come from the authenticated local SDK Status endpoint. Missing or omitted media preserves its caption and an attributed notice. This capability exposes no WhatsApp publication, reply, reaction, read or view operation and creates no conversation route. The active archive topic is protected against conversation route import/restoration collisions.

`bridge.Extensions.PassiveTopics` runs before ordinary text forwarding. Archive text/media receives guidance; edits and mapped reactions remain passive. Other commands retain their dedicated handlers, including `/clear`.

Status author preferences are separate from conversation modes. Mapped `/mute_status` and `/unmute_status`, plus `/mute`, `/unmute` and `/keep` in the archive, require master, owner, exact topic and retained reply evidence. Aliases resolve under the directory lock; the latest account-wide preference revision wins. Operation journals and frozen confirmations prevent retries from reapplying preferences. An unmute never replays skipped posts.

`/muted_statuses [page]` uses ten people per page, linked names and Unicode collation. Callback controls bind the owner, bot, account, destination/topic, expiry, preference revision and original confirmed presentation. Controls introduced by an edit require a confirmed edit receipt; refused or unfinished views cannot mutate preferences. Stale unmute buttons cannot reverse a newer preference. Callback acknowledgement and view replacement use fenced idempotent progress rather than ambiguous send effects; accepted preferences and independently queued edits survive acknowledgement failures.

Native SDK/real PostgreSQL fixtures cover passive delivery, local media, expiry, refresh/webhook races, frozen refresh recovery, uncertain sends/topic setup, migration gates, alias preferences, permanent skips, pagination, scopes/expiry, stale controls and callback/edit crash recovery. Explicit `run` composes these capabilities after native identity and callback verification; diagnostic `serve` remains passive.
