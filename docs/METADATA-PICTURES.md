# Metadata picture stages

`internal/metadata.Pictures` prepares and applies group/contact photo work after the text stages. The native OpenWA SDK reads group pictures and contact profile-picture URLs; native Telegram SDK models upload group photos and static bot profile photos. This is another independently resumable stage, not a complete `sync_metadata` handler. Permission actions, member-bot reporting, run fan-out/coalescing, owner commands, completion notices and scheduling still need implementation before runtime dispatch.

## Preserve unavailable pictures and shared chats

Missing, null and empty source URLs preserve existing Telegram pictures and prior cache evidence. Source lookup or download failures do not create a successful photo plan. Inbox groups never fetch or upload a group avatar, so WhatsApp metadata cannot replace the shared management group's picture. An unbound contact does not create a bot or direct route. Missing mirror permissions skip the photo stage for later scoped guidance without accessing WhatsApp pictures. Native mirror privacy and Change Group Info rights are checked again before upload; contact uploads validate the bound bot's native identity.

The downloader accepts only credential-free HTTPS URLs on the original WhatsApp/FB CDN domains. It sends no provider API key or authorization header and follows no redirects. Reads enforce actual bytes, declared size, cancellation and a timeout, with separate rate/transient failures. Signed URLs are not stored in plans, receipts, cache keys or assets.

Source bytes use SHA-256 content hashes. The cache also requires the current native Telegram photo's unique ID, so URL rotation alone does not re-upload a picture and later manual replacement is detected. Cache scopes include the permanent account, OpenWA session, canonical source identity, provider bot/destination and group return generation. A former mirror's cache cannot suppress uploads to a different destination. LID display numbers provide no phone evidence.

## Freeze bytes before uploading

The configured byte budget is capped at 8 MiB for metadata pictures. Static JPEG/PNG/GIF/BMP/TIFF/WebP inputs use Go codecs; JPEG bytes are retained after validation, and other supported inputs become a first-frame JPEG. `golang.org/x/image v0.48.0` was resolved as the latest stable codec release and pinned exactly. Image configuration is inspected before decoding, with a limit of 16,777,216 decoded pixels and maximum dimension 16,384. Both downloaded and converted bytes must fit the budget. Invalid, interrupted or oversized images cannot replace an avatar. These codecs and limits apply to metadata pictures; message/sticker codec workflows and their approved budgets remain separate.

Migration `00015_metadata_pictures.sql` stores content-addressed JPEG assets in account-scoped PostgreSQL `bytea` rows, complete photo plans and destination-scoped cache evidence. Asset and plan admission commit together under the current claim and account directory lock. The plan records source/asset hashes, target identity, session, route and return generation before any upload. Assets persist across worker/process restarts; retry never downloads or converts a replacement for a frozen upload. Account/claim, snapshot, route, generation, retirement and binding checks still apply before using that asset.

Uploads use ordinary durable effects and preserve uncertain outcomes for explicit review. A lost response, invalid acknowledgement or ambiguous provider error never becomes a confirmed cache entry or an automatic second photo upload. Definite rate refusal can retry the original persisted bytes. Completed upload receipts reconcile independently of later local writes.

After a confirmed upload, an independent read effect freezes the first available native photo ID. Cache persistence validates both effects, their job/scope and complete frozen requests. Cache and stage completion commit atomically. If cache persistence fails and a manual avatar change occurs later, recovery retains the original observed ID rather than associating the old source hash with that later avatar. If the native ID is unavailable, lookup retries without repeating the confirmed upload; acknowledgement alone is insufficient cache evidence.

Picture-stage completion does not complete a whole metadata run. Full run orchestration must serialize each metadata source stream, retaining unresolved uploads as a barrier to later automatic runs while keeping chat streams independent and prioritized. Frozen assets, plans, upload/read receipts and scoped cache entries must survive import/recovery; no automatic asset deletion is introduced here. No live provider request or service setting is changed by the isolated PostgreSQL/native SDK tests.
