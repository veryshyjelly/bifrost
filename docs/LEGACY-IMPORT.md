# Legacy state preparation

The TypeScript checkpoint is `checkpoint-typescript-baseline`. Its export format includes `manifest.json`, `bridge.env`, `telegram-api.env`, `data.tar.gz`, `media.tar.gz` and `telegram-data.tar.gz`. The export contains credentials and private messages. Keep it private and retain the original source resources.

The Go CLI can inspect an existing, frozen export without Docker, PostgreSQL, provider access or runtime configuration:

```sh
bifrost legacy-validate --file /private/path/bifrost-export.tar.gz
```

This validates the archive and SQLite snapshot. It does not import, start a worker, change webhooks or perform a cutover. Transactional PostgreSQL import and active compatibility for the remaining legacy journals are still being implemented. Successful validation does not establish runtime readiness.

The implemented PostgreSQL preparation stages can now be rehearsed together:

```sh
bifrost migrate
bifrost legacy-prepare --file /private/path/bifrost-export.tar.gz --session planned-openwa-session
```

Set `DATABASE_URL` to a fresh rehearsal database before either command. Preparation uses the archive's original permanent identity and encryption key; it does not load or replace them from a newly generated runtime environment. It never migrates the schema implicitly. The optional `--session` fixes the planned provider connection; omission retains the original connection. Exact replay must keep that choice.

The command composes source preparation, credentials, directory, routes, completions, retained messages/sources, edits and incoming/outgoing interaction state. Each capability commits atomically. If a later capability fails, earlier checkpoints remain inactive and repeating the exact command resumes them without resetting state. Failure output names the capability without exposing the private database/source error. Success reports completed capability names and `ready: false`: remaining journals, external asset restoration and runtime composition still prevent activation. This command is a preparation rehearsal, not a finished import or cutover command. No provider calls, worker, webhooks or scheduler start.

The command prints the permanent account, archive/SQLite SHA-256 digests, row counts, durable domain counts and job/effect state counts. It omits tokens, encryption keys, provider URLs, raw payloads and errors. `sending` effects and `running` jobs remain unchanged during inspection; the report does not claim they completed or become safe to replay.

Python 3.11 or newer with its standard `sqlite3` module is required; the existing codec runtime image already includes it. The reader uses embedded trusted code in an isolated interpreter, a read-only connection, a transaction, an authorizer and SQLite size limits. It never loads an archived script, runtime or environment. It includes committed WAL data and checks the complete database integrity. A callback receiving rows must wait for the reader's final digest and cross-row validation before committing anything.

The permanent account comes from the saved identity, checked against `BIFROST_ACCOUNT_ID`, then the configured original account or original OpenWA session. A rotated provider connection never replaces a saved account. Telegram API credentials must match both private files, and every saved bot token must decrypt with the original key and match its bot ID. Original encrypted strings and file bytes are preserved. Alias validation uses explicit evidence; a LID display number never becomes a phone identity.

Extraction uses a fresh private staging directory and removes only that directory on completion or failure. Files become `0600`, directories `0700`; archived executable permissions and ownership are ignored. Component hashes, gzip checksums and complete tar streams are checked. Absolute/traversal paths, links, special files, duplicate paths, unexpected outer files, hidden trailing data, concatenated gzip members and conflicting file/directory paths are rejected. No source file or volume is deleted or rewritten.

Default limits are 64 GiB compressed archive, 256 GiB total expanded content including archive metadata, 64 GiB per file, one million archive entries and one million SQLite rows. Use `--max-archive-bytes` and `--max-expanded-bytes` to lower or explicitly increase the corresponding limits for a known export. `--scratch DIRECTORY` chooses the parent of the owned private staging directory. Ensure sufficient free space for retained Telegram and media files.

The semantic snapshot reader recognizes all 55 durable KV domains and 18 current legacy job types. It rejects unknown domains/types, malformed JSON, conflicting alias/bot bindings, unregistered bot references, wrong private/group control scopes and ambiguous group message mappings. It retains exact integer IDs and source JSON strings. It does not fabricate missing provider requests or receipts from the older effect table, which did not store them.

The internal PostgreSQL preparation API is tested separately from activation. Migration 31 stores an archive/account checkpoint, exact append-only rows from all six source tables, exact KV value strings and an encrypted copy of both original environment files. Preparation accepts only an empty business schema with the same permanent account/key, or creates that identity within the same transaction. It serializes identity and queue admission, refuses concurrent destination writers, and commits only after final SQLite/digest/cross-row validation. A late source error, COPY failure or projection error rolls back the complete preparation, including a newly created identity.

The exact same archive can be prepared again without changing its first result or resetting subsequent work. A different archive cannot merge into that checkpoint. Source rows, KV values and checkpoint identity are protected against updates/deletion. Until native journal projection and external asset restoration are complete, the checkpoint has no activation marker: both explicit runtime readiness and the SQL claim query block dispatch for the account. Preparation does not insert runnable legacy jobs or fabricate native effects. This internal API is not exposed as a finished import CLI yet.

The credential projection is implemented independently in migration 32. It copies member ciphertext strings exactly, seals the original plaintext master token with the original key, preserves member Start activation and registration names, and records immutable hosted-logout proof scoped to account/bot/credential revision. Cached Telegram identity and Start alone never create logout proof or local migration eligibility. An imported `migrated=true` permits native setup to skip only the already confirmed hosted logout; the configured local API must still return a valid native `getMe` result before lifecycle eligibility is persisted and webhooks/menus proceed. A credential revision change cannot reuse the imported proof. Failed local checks leave eligibility absent and retry without repeating confirmed logout. Projection replay returns its first result without overwriting a later credential change, and any projection error rolls back credentials and proof together. Import activation remains blocked while other journals/assets are pending.

Migration 33 adds the identity/mention projection after credentials. It preserves explicit normalized aliases, original contact profiles and metadata-sync evidence, canonical contact bindings, copied token keys and original group roster members/timestamps. A binding keeps its selected source profile separately from its canonical routing identity, so an aliased contact's bound display name is retained. Unconfirmed source display updates cannot replace it; a confirmed native metadata refresh can supersede the imported name preference. Contact display numbers and cached roster `canonical` fields never establish phone evidence. Copied tokens and roster keys must match the permanent account digest and their original group scope. Missing bot prerequisites, foreign scope and existing native identity data are refused. A roster-write failure rolls back aliases, profiles, bindings and tokens together. Repeating a completed projection preserves later native names and newer rosters. The account remains inactive until the remaining workflows and assets are covered.

Migration 34 adds existing route state after the directory: all five modes, canonical WhatsApp identity, original Telegram destinations, retired-private-inbox flags, saved inbox references, mirror return generations and topic-name caches. The explicitly planned OpenWA connection scopes imported metadata caches; it never replaces the permanent account. Exact replay cannot change that planned connection or reset later native route changes.

Retired-topic keys contain a hash of the original Telegram management chat/thread rather than a plain topic ID. Projection matches that hash against retained topic coordinates from confirmed effects, Telegram receipts/observations, frozen targets, saved feed coordinates and route/inbox references. These coordinates identify existing source reservation state; they are not adopted as native send receipts. Missing exact evidence blocks projection. A source crash can leave a route pointing at its own confirmed retired topic: projection retains that route and reports pending retirement, with the permanent native reservation still blocking reuse. It does not recreate the topic or clear the route early. Conflicting topic ownership or alias-convergent routes are refused. Route/inbox/reservation/generation/cache writes and the immutable capability checkpoint commit together, or roll back together. Import activation remains pending alongside retained-message journals, controls, jobs and assets.

Migration 35 projects explicit `wa-complete=true` markers as account/chat/message completion evidence after route projection. Device suffixes and colons inside message IDs remain intact. False markers, mappings and uncertain effects never establish completion. Native and text live relays check this evidence before creating a new plan, preserving the legacy suppression of duplicate webhook deliveries even when the old send request was not retained. An existing frozen native/text plan takes precedence and must still reconcile its own work. Explicit history-all delivery uses its own run/copy scope and remains available for completed live sources. Projection does not fabricate provider receipts, resolve uncertain jobs or activate the import; its evidence and checkpoint commit together and completed replay is harmless.

Migration 36 projects retained message copies and cleanup observations. It preserves physical copy order, exact observation sequence IDs, private bot scopes, media flags, original formatting/mention evidence, cleanup dates/expiry/errors and the original verified self phone. LID display numbers cannot become self phone evidence. Cached provider receipts retain their complete original JSON, including fields the current SDK does not decode. Confirmed effect receipts require an unambiguous bot scope; unknown effects are never adopted. A mapping without a retained provider response keeps a JSON-null receipt and explicit `mapping-only` provenance. Actual original Telegram updates remain separate observation/source payloads, so their bot-scoped file IDs can be reused without pretending the user message was a send acknowledgement.

Group copy locations must agree with retained observations, receipts or frozen requested targets; missing or conflicting evidence blocks projection instead of borrowing the current route's topic. Confirmed retired topics make corresponding observations unavailable. Imported media flags and presentation fields feed native caption edits, reaction targets and owner revocation choices even when a full provider receipt is absent. Legacy copies without frozen plan groups retain their newest-row reaction target; native plan groups keep their existing attachment preference. Sequence advancement uses [transactional `ALTER SEQUENCE RESTART`](https://www.postgresql.org/docs/current/sql-altersequence.html), preserves exact large IDs and never rewinds an existing counter. Rows, verified self identity, sequence changes and the capability checkpoint roll back together on failure. Repeating a completed projection preserves subsequent observations. Remaining job/effect/control/history/metadata/Status journals and asset restoration still gate full activation.

Migration 37 retains the sender/context subset actually present in `wamessage`: canonical and original chat, message/sender/link identities, original name, ownership/history/Status flags, timestamp and mention evidence. It does not invent body or quoted content absent from that journal. Participant `/create` replies can use this retained identity when no job-linked native source exists. Harmless unbound display caches, including older group/unknown-sender names, remain display profiles; only person identities can bind contact bots and no display number becomes phone evidence.

An own-account group/Status sender can be proved from retained or native source snapshots without converting its LID into a phone identity. This proof lets a matching confirmed reaction echo retain its actual actor when the provider uses a different own-account JID. Outgoing private snapshots cannot prove the recipient is self. Echo target, emoji, age, account and confirmed-operation rules remain in force; source projection creates no echo acknowledgements. Sender/context rows and their immutable checkpoint commit together, and full import activation remains gated.

Migration 38 projects retained latest edits, confirmed outbound-edit hashes and explicit revocation markers. The latest-edit overlay preserves empty bodies and distinguishes omitted mention evidence from an explicit empty array. Native history/source normalization reads it before using stale original text. A subsequent native edit takes precedence, inherits unspecified mentions and can explicitly clear them. Retained edits remain immutable source evidence with no synthetic job or provider acknowledgement. Conflicting alias-convergent edit/hash caches are refused because their saved values have no timestamps to establish ordering.

Confirmed outbound hashes suppress only matching account/chat/message/body edit echoes. Explicit true revocation markers become native tombstones; false values, mappings and unknown operations do not. Tombstones prevent later source edits and copies, without marking existing Telegram copies deleted or creating new deletion work. The edit overlay, outbound hashes, tombstones and immutable projection checkpoint commit together. Failure rolls everything back; replay preserves later native edits. This stage creates no jobs/effects and does not activate the unfinished import.

Migration 39 restores poll selection arrays and cached standard equivalents for custom emoji. Poll options retain their exact order, whitespace and text, including an explicit empty selection; conflicting alias-convergent arrays are refused instead of guessing which is newer. Custom equivalents must pass the native single-emoji validator. Subsequent native votes and cache updates supersede imported mutable state, and replay never resets them.

Outgoing reaction resolution is retained separately by its original account/bot/event digest. Native handling reuses the saved emoji, explicit removal or unsupported result without fetching a replacement custom equivalent. Tuple hashing preserves the original JavaScript JSON string representation, including unusual account characters. A frozen resolution creates a pending native plan, not a completed operation: original pending/sending effects remain unresolved in source evidence. It does not manufacture send receipts or reaction echoes. Poll/cache/resolution writes and their immutable checkpoint roll back together; complete import activation remains gated on remaining journals and assets.

Migration 40 projects incoming reaction actor state, source echoes and confirmed Telegram setting/refusal caches. Original source hashes must match message coordinates retained in copies, compound-key values or original WhatsApp jobs. Echoes require the exact bot/chat/message copy and its retained thread; cached settings/refusals require a copy of that source in the hashed destination. A current route cannot substitute for missing coordinates. Private bot scopes remain distinct even when their numeric message IDs overlap. Missing evidence, conflicting alias-convergent state and foreign targets are refused.

Actor revisions/order, original event keys and represented user echoes survive. When two proven actor aliases occur within one state, their shared revision counter selects the newer reaction; independent alias caches have no shared ordering and conflicting values are refused. Imported state records only the known actors and does not invent evidence that absent actors were removed by a full snapshot. Confirmed destination signatures retain their exact message/emoji and refusal time/reason; the older cache did not retain an applied actor identity, so none is invented. Native reaction input consumes these facts and later events advance them normally. Repeating projection never resets later native state.

An unfinished fallback notice remains an immutable reference to its original reaction job, source and destination. Its original job must match the saved conversation/message; projection does not send it, declare it complete or drop it. Resuming that notice still requires the remaining original job/effect/notice compatibility stage. Actor state, echoes, caches, pending references and the capability checkpoint commit or roll back together. Full activation remains blocked, and projection creates no native jobs, send effects or synthetic acknowledgements.

Migration 41 restores the saved Status feed topic, mute records/counter, original mute-operation results and permanent skipped-post hashes. Feed ownership is visible to native topic reservation checks without manufacturing a topic creation job or receipt. Mutes use explicit alias evidence and the latest saved revision; the global counter must cover all saved revisions. Repeating an original mute job returns its saved result without applying a second change or advancing the counter. New operations continue above the imported counter.

Skipped hashes remain usable even for muted posts that were never enqueued and therefore have no retained message ID. Native receive and refresh check them and explicit completed-post markers before new delivery. Unmuting cannot resurrect those old posts. Reply commands use the original retained Status sender/context when a job-linked native post is absent; no missing body is invented. Feed/mutes/counter/operation/skip state and their checkpoint commit together or roll back together. Replay preserves later native changes. The preparation command includes this stage but still cannot activate delivery or restore external assets.

Create a source export with the historical procedure in [MOVING.md](legacy/MOVING.md) from the checkpoint. That procedure quiesces the source writers and preserves all original volumes. Do not archive a changing SQLite database by copying its main file alone. OpenWA session state requires its separate documented migration; it is not part of a Bifrost legacy export. No live export, import or identity cutover is performed by these preparation checks.

SQLite behavior references: [read-only WAL databases](https://sqlite.org/wal.html#read_only_databases), [Python read-only URI connections](https://docs.python.org/3/library/sqlite3.html#how-to-work-with-sqlite-uris).
